# UofT GPLLM Calendar

<img src="/public/images/og-image.png" alt="graph image" width="500">

A simple static website for the University of Toronto GPLLM program calendar. 

Built with [Astro](https://astro.build) and [Alpine.js](https://alpinejs.dev). Optimised for minimal Javascript footprint, performance, a11y, and SEO.

## Stack

- **Astro 6** — static output, client-side routing via `<ClientRouter />`
- **Alpine.js** — lightweight interactivity, no build step
- **Plain CSS** — custom properties, fluid type scale, no framework
- **Bun** — package manager and script runner


## Quickstart

```bash
bun install    # requires node 22+
bun dev        # local development
bun run build      # outputs to ./dist
bun run preview    # preview the ./dist build locally
```

## Content and last-updated dates

Page content lives in `src/content/*.toon`, except the calendar's schedule, which
lives in `src/lib/calendar-data.ts`. Every page shows the same date, read from
`src/content/modified.toon`:

```
site: 2026-09-13
```

That file is stamped automatically. A pre-commit hook checks whether any content
file is staged, sets the date to today, and adds the change to the same commit,
so the date always ships with the edit that earned it.

```bash
bun install       # also wires up the hook (see below)
bun run stamp     # stamp manually, without committing
```

Hooks live in `.githooks/` rather than `.git/hooks/`, so they are shared through
the repo. The `prepare` script points git at them via `core.hooksPath` on every
install. Nothing extra is needed on a fresh clone beyond `bun install`.

Three things to know:

- The hook only fires on local commits. Edits made through the GitHub web UI will
  not stamp a date.
- Content outside `src/content` has to be listed in the `EXTRA` array in
  `scripts/stamp-modified.ts`, or changes to it go unstamped.
- Dates are derived at commit time, not build time. Reading them from `git log`
  during a build looks tidier but breaks on hosts that do a shallow clone, where
  every file reports the same single commit.

## Deployment

Assuming a static site host like Cloudflare Pages, Github Pages, Netlify, etc.

- Build command: `bun run build`
- Set output directory: `dist`
- Ensure Node version is set to **22** or higher in environment settings
- Add any environment variables (none by default)

No build-time scripts beyond `bun run build` are needed. The `prepare` script runs
during install and only configures local git hooks, which is a harmless no-op on a
build host.

### Cloudflare Pages

This site is deployed (and optimized for deployment) using [Cloudflare Pages](https://developers.cloudflare.com/pages/). This involves:

- `public/_headers` sets the security headers (including the CSP) and all
  cache-control
    - `/sw.js` has `max-age=0, must-revalidate`, which is what lets a stale client discover a new worker
    - `/_astro/*` set as immutable, since those filenames are content-hashed
- `public/_redirects` 302 redirects `/` to `/calendar/`
  - Astro's `trailingSlash: 'always'` matches how Pages serves directory routes, so cache keys and canonical URLs agree
- Pages keeps the assets of previous deployments reachable
  - That makes a mid-deploy session safe: a page from build `n` can still fetch build `n`'s hashed assets after build `n+1` is live
- Cloudflare's basic analytics injects `static.cloudflareinsights.com/beacon.min.js` into every HTML response
  - The CSP allows the script and its `cloudflareinsights.com` reporting endpoint
  - Browsers with tracking protection (Firefox ETP, most content blockers) block
  the beacon client-side

## PWA and caching strategy

The site is installable via iOS Safari's _Add to Home Screen_ (and equivalents
on Android/desktop) and works offline.

A service worker generated by
[`@vite-pwa/astro`](https://vite-pwa-org.netlify.app/frameworks/astro.html)
(Workbox `generateSW`) manages two kinds of cache, split by how the content
changes:

- **Hashed assets** (`_astro/*` js/css, fonts, icons, manifest) are
  precached at install
  - Their filenames change when their bytes do, so serving
  them cache-first is always correct
- **Pages** are never precached
  - They are served network-first with a 4 second
  timeout, falling back to a cached copy
  - i.e. an online visitor always gets the deployed HTML with its real headers, and an offline one gets the last good copy
  - `public/sw-warm.js` seeds the three pages at install so offline works
  before a first visit, and clears runtime caches


### Service worker and precache

HTML is excluded from the precache deliberately. A precached page is replayed
whole, response headers included, which pins a client to the deploy its worker
installed from: content, CSP, and asset URLs all freeze together until a full
worker update completes on that device, and any interrupted update mixes pages
and assets from different builds. Network-first pages dissolve the whole
class: content-only deploys are visible on the next load with no worker update
involved, header changes propagate immediately, and the worker itself only
changes when hashed assets do.

The pages route matches same-origin requests that are either real navigations
or paths ending in `/`, because Astro's `<ClientRouter />` swaps pages with
plain `fetch()`es that are not `mode: 'navigate'`. The `.ics` files are not
cached at all: `webcal://` subscriptions are fetched by the OS calendar app,
which no service worker ever sees.

Updates use `registerType: 'autoUpdate'`: a new worker activates and takes
over immediately, but `PWAUpdatePrompt.astro` suppresses the default reload in
favour of a toast. Because client-side routing never triggers the browser's
own worker update check, the component asks explicitly on every page load, on
tab focus, and hourly. When a new worker lands mid-session, every link is
stamped with `data-astro-reload` so the next click is a full navigation and
markup never runs against a bundle from a different build.

The worker is disabled in dev (`devOptions.enabled: false`), and the dev
build actively unregisters any worker left over from earlier configurations.
Use `bun run build && bun run preview` to test caching behaviour.
